# FastInfo

Public website and admin dashboard for FastInfo, a technology retail, printing/typing, and event
photography business in Antananarivo, Madagascar.

Stack: Next.js (App Router) · TypeScript · Tailwind CSS v4 · shadcn/ui · Supabase (Postgres, Auth,
Storage) · React Hook Form · Zod.

## Running locally (demo mode)

No setup required. The app falls back to fixture data in `src/lib/demo/fixtures.ts` whenever
Supabase credentials are absent, so the full public site is browsable immediately:

```bash
pnpm install
pnpm dev
```

Open http://localhost:3000. The admin dashboard (`/admin`) is the one part that needs a real
Supabase project — see below.

## Connecting a real Supabase project

1. **Create a project** at [supabase.com](https://supabase.com).
2. **Run the migrations**, in order, via the SQL Editor (or `supabase db push` with the CLI):
   - `supabase/migrations/0001_schema.sql` — tables, enums, triggers
   - `supabase/migrations/0002_rls.sql` — row-level security policies
   - `supabase/migrations/0003_storage.sql` — the public `media` storage bucket
3. **Seed demo content** (optional but recommended) by running `supabase/seed.sql` in the SQL
   Editor. It inserts the same products, services, offers, gallery photos and events used in demo
   mode (regenerate it after editing fixtures with `pnpm seed:generate`).
4. **Fill in `.env.local`** (copy `.env.example`):
   ```bash
   NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon-key>
   ```
   Both values are in Project Settings → API. Restart `pnpm dev` after saving.
5. **Create your admin account**: sign up once from `/admin/login` is not available (there is no
   public sign-up form by design) — instead create the user directly in the Supabase dashboard
   under Authentication → Users → Add user, then promote it. The `prevent_role_escalation` trigger
   (see `0001_schema.sql`) blocks role changes unless run by an existing admin's authenticated
   session — which doesn't exist yet for the very first admin — so the SQL Editor needs to
   temporarily disable it for this one bootstrap update:
   ```sql
   begin;
   alter table public.profiles disable trigger trg_prevent_role_escalation;
   update public.profiles set role = 'admin' where id = '<user-uuid>';
   alter table public.profiles enable trigger trg_prevent_role_escalation;
   commit;
   ```
   Every new `auth.users` row automatically gets a `profiles` row with role `viewer` (same
   trigger file); promoting to `admin` is the one manual step, by design — nothing in the running
   app can self-escalate a viewer to admin. Once you have one admin, promoting further accounts
   can be done from an authenticated admin session instead (e.g. a future admin-users page), which
   doesn't need this workaround.
6. **Sign in** at `/admin/login` with that account's email and password.

The service-role key is never used by the running app — every write goes through the authenticated
admin's own session, gated by RLS. It's only needed once if you choose to run bulk imports outside
the SQL Editor.

## Project structure

```
src/
  app/
    (public)/     public site — home, catalogue, services, gallery, events, contact
    admin/
      (auth)/      /admin/login — outside the admin layout, no auth guard
      (dashboard)/ everything else under /admin — guarded by requireAdmin()
  components/
    public/        public site components (cards, hero sections, gallery/lightbox)
    admin/         admin dashboard components (tables, forms, image tools)
    media/          SmartImage — the one place aspect-ratio/placeholder/fallback logic lives
    ui/            shadcn/ui primitives
  lib/
    data/          server-side readers; each falls back to lib/demo/fixtures.ts when
                   Supabase isn't configured (see lib/supabase/env.ts)
    actions/       server actions (mutations) for the admin dashboard; every one calls
                   requireAdmin() first — the admin layout's check alone is not sufficient
    media/         MediaProvider abstraction over Supabase Storage; swap providers by
                   implementing the interface in provider.ts, nothing else changes
    validation/    Zod schemas, shared between client forms and server actions
    demo/          fixtures.ts (demo content) + images.ts (curated Unsplash photo ids)
  types/
    database.ts    hand-written to mirror the SQL migrations — regenerate with
                   `supabase gen types typescript` once a live project exists and diff
                   before replacing
    domain.ts      the shapes the app actually renders (joined, image URLs resolved)
supabase/
  migrations/      run in order against a fresh project
  seed.sql         generated by scripts/generate-seed.ts — do not hand-edit, re-run instead
```

## Security model

Four independent layers, deliberately redundant:

1. **Middleware** (`src/proxy.ts`) redirects unauthenticated visitors away from `/admin/*`.
   Convenience only — it can be bypassed by calling a server action directly.
2. **`requireAdmin()`** (`lib/supabase/guard.ts`) runs in the admin layout *and* at the top of
   every server action. It calls `auth.getUser()`, which re-validates the JWT against Supabase,
   never `auth.getSession()`, which only trusts the cookie's own claims.
3. **Row-level security** on every table: anonymous/authenticated users can `select` published
   rows only (offers additionally check `starts_at`/`ends_at` against `now()` in the policy
   itself, not in application code); every write requires `is_admin()`.
4. **Storage policies** on the `media` bucket: public read, admin-only write. Uploads go directly
   from the admin's browser to Storage under their own session — the service-role key never
   appears in application code.
